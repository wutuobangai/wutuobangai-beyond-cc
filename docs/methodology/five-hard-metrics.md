# 五件硬指标：缺一件就是半成品

> 一个任务"做完了"和"真完工了"，差的不是态度，是五件可核验的证据。缺一件，就是半成品，必须打回。

我不写代码，但我每天靠一群 AI 替我跑公司。早期最大的坑，是 AI 跟我说"完成了"，我信了，过两天客户用着报错——它其实只做了一半。后来我把"完工"这件事拆成五件硬指标，每件都要拿出证据，缺一件就退回去重做。这套标准把"自报完成"变成了"可核验完工"，下面拆给你看。

## 真实场景：自报完成 vs 真完工

同样一句"功能做好了"，弱团队和强团队的差别全在动作上。

| 环节 | 第一反应（半成品思维） | 正确动作（完工思维） |
|------|----------------------|---------------------|
| 验证 | 凭感觉判断没问题 | 跑一遍，截图返回值，贴出可核验证据 |
| 记录 | 改完就走，下次全靠记忆 | 当场写盘：变更日志 + 沉淀文件 |
| 复用 | 知识留在这次对话里 | 接入索引入口，下次能被搜到 |
| 同步 | 等人问起才说 | 主动汇报，附证据路径 |
| 上线 | 本地能跑就算完 | 推到真实环境再验一次 |

凭主观判断"差不多了""没问题了"——这类话就是半成品的信号。真完工不靠感觉，靠五件证据。

## 为什么会这样：五件硬指标拆解

完工不是一个模糊的"差不多"，而是五个独立的、各自有证据的关口。任何一关交不出证据，整件事就退回。

| # | 硬指标 | 它在堵什么漏洞 | 可核验证据 |
|---|--------|---------------|-----------|
| 1 | 真验证通过 | 堵"自报完成"——没跑就说好了 | 关键标记搜得到 / 接口返回正常且内容对 / 数据库查得到记录 / 文件确实生成 |
| 2 | 沉淀写盘 | 堵"知识蒸发"——下次从零再来 | 变更日志记一行 + 沉淀文件落盘（带原话和时间戳） |
| 3 | 入口接入 | 堵"沉淀了却搜不到"——等于没沉淀 | 把这条接进多个固定索引入口，下次一搜就出 |
| 4 | 主动汇报 | 堵"闷头干"——做完不说，没人知道 | 主动发出完工通知，附五件指标清单 + 证据路径 |
| 5 | 部署验真 | 堵"本地能跑线上挂"——交付即翻车 | 推到真实环境后再验一次，确认线上真的生效 |

它们之间是一条因果链：验证保证"这次真的对"，写盘保证"这次不白做"，入口保证"以后找得到"，汇报保证"协作不断点"，部署保证"交付能落地"。少任何一环，链条就断在那里——验证漏了会带病上线，写盘漏了下次重复踩坑，入口漏了沉淀变废纸，汇报漏了协作出黑洞，部署漏了客户第一个发现问题。

这五件之所以是"硬"指标，因为每一件都要拿出客观证据，不接受主观判断的过关。证据可以被任何人复核，这才挡得住自欺。

## 你该怎么做

把这套标准照搬进你的协作流程，让"完工"变成可验收的动作：

1. 收到"做完了"先别信，按五件指标逐项要证据。
2. 验证那一关，要求贴出可核验的返回值或记录，不接受口头保证。
3. 改完当场写盘，变更日志记一行，关键决策落进沉淀文件。
4. 把沉淀接进固定索引入口，确认下次搜得到，否则等于没沉淀。
5. 完工主动发汇报，附上五件指标清单和每件的证据路径。
6. 凡是要上线的，推到真实环境后再验一次，确认线上真生效。
7. 任何一件交不出证据，整件事退回重做——缺一件就是半成品。
