# 几个 AI 怎么分工：先看任务有没有标准答案

> 作者：阿浩 · 2026-11-18 首写 · 2026-11-26 更新

你开了几个 AI 窗口，一份稿来回贴，谁都说自己能做。忙了一圈，最后还得你把几份答案拼起来。多一个工具，未必少一份活。

我现在先看任务是什么，再定谁做。代码能跑、链接能开，这些有比较明确的检查办法；选题和口吻，则要看作品是不是我想表达的。两类任务不能都按“谁回得最快”来分。

## 已经在用的分法

下面是我自己的使用安排，更新到 2026-11-26。它记录我怎么做事，不是模型能力排名，也不保证你的任务照搬就合适。

| 工作 | 我现在主要交给谁 | 怎么看结果 |
|---|---|---|
| 代码修改、执行具体任务 | Claude / Claude Code | 对照改动，运行检查，再走实际功能 |
| 中大型或安全相关代码审查、可视化操作 | GPT / Codex | 带原任务和产物，按实际证据核对 |
| 联网找资料、查公开信息 | Grok Bot | 回到原始来源，核时间和适用范围 |
| 自媒体选题、口播与前端内容 | Gemini | 对照原意和素材，看成稿、看样片 |

我以前的文章重点写 Claude 和 Codex 两边配合。现在工具多了，仍然保留一个要求：需要独立核对的活，别让施工方自己宣布全部通过。被叫作“审查方”，也不等于自动拿到了上线、付款或删文件的权限。

## 有标准答案，带着证据交；主观创作，带着样稿交

代码任务先说清触发条件和想要的行为。执行方交改好文件、检查结果和未验项。审查方从原目标出发查遗漏，不能只看对方的总结。

创作任务先给原始材料、受众和想表达的意思。先看一段稿或一段样片，确认方向再往下做。几个 AI 各写一版，最终谁接收、用什么标准选，也要提前说清，不然我又成了搬运工。

小事一条线做完。值得分出去时，才划开可改文件；同一份文件需要接着改，就排先后。联网查证的答案也要带来源，搜索摘要不直接当事实。

## 给 AI 派活的任务单

“帮我优化一下”留了太多空白。AI 不知道你要改哪份、不能碰哪块、做到哪算完，往往会替你补决定。原来的八个字段，我现在补成下面这张单，复制后把空白填上就能用。

```text
任务名：____
原始目标：____（读者／使用者最后要看到什么）
已定条件：____（已认可的版本、结构、内容，不能擅自换）
对象与输入材料：____（文件、版本、材料位置）
负责人：____；接收结果的人：____
只读范围：____
允许修改的目录／文件：____
禁止动作：____（明确是否允许外发、上线、删除、付款等）
依赖：____（前一步交了什么，才能做本步）

交付物与位置：____
完成条件：____（正常路径、失败路径分别怎样才算对）
验法与证据：____（打开哪里、做什么、应看到什么）
限时：____；费用上限：____（未写明获准额度就不付费调用）

失败、额度用尽或资源不足：停相关动作，保留结果和原因；
独立且已获准的部分继续做，不自动换付费路线。
发现范围外问题：只列问题和建议，不顺手扩大范围。
断线后：先核真实文件、进程和结果，再续；不重复执行。
并行时：不回退别人改动；同一份文件先确认谁在写。
交付时说明：改了什么、怎么验、未完／未验、需要谁决定。
独立核对方（需要时）：____
```

模板里的“禁止动作”要具体。只准改本地文件，就不能把“功能做完”理解成顺便上线。已经明确获准的同一件事，则做到约定终点，不必每一步重新问。

## 可直接抄走：一个填好的小例子

下面是虚构任务，文件和目录都只是样例：

```text
把 sample-guide/里的“示例-使用说明.md”补成新手看得懂的说明。
只改这一份，保留已确认的章节顺序，不改程序和价格。
材料用“示例-功能清单.txt”；缺事实就标待补，不编功能。
交付仍放原位置，附不超过五行的改动与未验说明。
在二十分钟内完成，不付费、不联网发送、不上线、不删文件。
验法：逐项对照功能清单；本地预览，检查新链接对应正文。
卡住先保留已做部分，告诉接收人缺哪项输入。
```

真做长任务时，再留一份[最小接续单](/methodology/minimal-resume-note.html)。任务单说清要做什么，接续单说明已经做到哪，别让每个新窗口都从猜开始。
