# AI 做视频把系统盘塞满了，哪些该留？

> 作者：阿浩 · 2026-11-26

视频还没出完，系统盘先红了。你让 AI 清理，它列出一串缓存目录，可你不知道哪个删了还能再来，哪个删了就得重做。

我也碰过这件事。做视频留下的帧序列、试渲染和放大中间件，能比成片大得多。后来我把“这次做出了什么”和“过程里临时生成了什么”分开管。下面的目录和任务全是虚构示例。

## 先查占用，再判断价值

一个叫 `spring-film` 的任务，可以这样放：

```text
spring-film/
  成品/        已确认的视频、封面、交付说明
  工程与素材/  源码、项目文件、原始素材、字体与授权说明
  过程/        临时帧、缓存、试渲染、中间文件
  经验/        这次为什么失败、下次怎么避免
```

文件叫“缓存”，不等于现在就能删。某个工程可能还在引用它；所谓原始素材，也可能只是别人发来的唯一一份。先列出大小、生成来源、引用方，再决定归哪类。

我会先问 AI 一句话：“这个文件没有了，你靠什么重生成？”它要说清源码在哪、原素材在哪、依赖是否还在。答不出来，就先保留。

| 文件 | 判断时看什么 | 比较稳的处理 |
|---|---|---|
| 已确认成品 | 是否已完整播放、能否交付 | 留存，并做独立备份 |
| 源码与工程 | 能否重新打开、素材引用是否有效 | 连同原素材保留 |
| 帧序列与渲染缓存 | 是否能用现有工程重生成、是否还在渲染 | 核实后再列清理候选 |
| 废版本、试片 | 是否有无法重做的片段、有没有人还要看 | 先隔离留存，定期确认 |
| AI 旧对话 | 是否保留决策、授权、失败线索 | 单独归档，不当渲染垃圾清理 |

## 工作盘有位置，也要让程序真的写进去

文件夹建在工作盘，不代表渲染器的缓存也在那里。输出目录、临时目录、帧序列目录，得分别核。先做一小段，看看实际生成文件落在哪，再开长片。

盘没挂上就暂停。不要让程序悄悄回落到系统盘继续写。空间预算也要包含过程文件：成片很小，不代表渲染高峰只需要那么多空间。没有实测，就先做短段，观察峰值再估。

正在跑的任务先查进程和输出时间。另一个窗口还在渲染时，不能因为这里看着像旧文件就动它。两项任务的过程目录也要分开，免得一边清、一边读。

## 需要搬家，先复制，再核引用

跨盘挪文件，最怕工程仍指着旧位置。比较稳的顺序是：先复制到新位置，核文件数量和大小，重要文件核指纹；再改工程引用，重新打开并试渲染。原位置怎样处理，等确认和授权后再做。

旧对话另放一处。它们通常占空间，却也保留了“为什么这样做”。要归档就核能否找回、能否阅读、备份是否完整，别混进“到期清空”的目录。也别为了腾空间就随手改 Git 历史，工程里的大文件要另查引用和备份。

## 一张清单比一句“清完了”有用

```text
任务：spring-film（示例）
成品和工程位置：____
原素材、依赖与备份核验：____
正在运行／可能引用这些文件的任务：____
可重生成候选：____（依据____）
不能重生成、先隔离的文件：____
旧对话归档位置及回读结果：____
本轮允许处理哪些具体对象：____
处理后空间、工程打开与试渲染结果：____
未确认的对象继续保留，不按文件夹名字猜。
```

想先看占用，可以用 [AI 垃圾体检](/projects/#ai-垃圾体检-ai-junk-check)：它只检查、不动你的文件，告诉你哪一类占了多少。报告里有本机路径，别直接发给别人。真要清的时候，也别把回收站当成什么都能找回来的保证。
